# EGT Database Guide (PostgreSQL + Prisma)

Source of truth: `apps/backend/prisma/schema.prisma` (PostgreSQL, Prisma ORM).
Migrations live in `apps/backend/prisma/migrations/`.

**Status:** schema migrated with `prisma migrate deploy` against real PostgreSQL 16
(2026-09-25). Dev seed exists (16 audit-verified products, 4 roles, 5 dev users).
No production database provisioned (needs-from-Sukh).

---

## 1. Conventions

- **Primary keys:** every table uses `String @id @default(uuid())` — UUID v4
  generated by Prisma (join tables use composite `@@id`).
- **Soft deletes:** most business tables carry `deletedAt DateTime?`. Soft-deleted
  rows are excluded from normal queries; nothing is hard-deleted except
  cascade-owned children and ephemeral session/token rows.
- **Audit fields:** business tables carry `createdBy` / `updatedBy` (user UUIDs,
  plain strings, nullable) plus `createdAt` / `updatedAt`. Who-did-what at the
  action level lives in the append-only `AuditLog` table.
- **Human-readable numbers:** RFQs, orders, shipments and support tickets get
  transactional **yearly-sequential** numbers (`EGT-RFQ-2026-000001`,
  `EGT-ORD-2026-000001`, `EGT-SHP-2026-000001`, `EGT-TCK-2026-000001`),
  allocated atomically inside the create transaction via the `*Sequence` tables
  (`year` PK, `nextVal`) — no gaps on retry, no collisions under concurrency.
- **Money:** `Decimal(18,2)` for money, `Decimal(18,4)` for quantities/prices.
- **Secrets at rest:** refresh tokens stored as SHA-256 hashes (never raw);
  passwords as argon2id hashes; document filenames randomised; verification
  tokens stored as SHA-256 hashes.

## 2. Entity map

### 2.1 Identities & access

| Model | Key fields | Relations |
|---|---|---|
| `Role` | `name` enum: buyer / supplier / staff / admin | → `User[]`, → `RolePermission[]` |
| `Permission` | `key` unique (e.g. `rfq.approve`, `admin.users.read`) | → `RolePermission[]` |
| `RolePermission` | composite PK `[roleId, permissionId]`, cascade deletes | Role ↔ Permission join |
| `User` | `email` unique, `passwordHash` (argon2id), `roleId`, `isActive`, `emailVerifiedAt`, `failedLoginCount`, `lockedUntil`, `lastLoginAt`, `companyId?`, soft-delete | → Role, → Company?, → Session[], → RefreshToken[], → DeviceToken[], → NotificationPreference[], → ConversationParticipant[], → Message[] (sender), → AuditLog[] (actor), → SupportTicket[] (requester + assignee), → Supplier[] (owner), → Rfq[] (buyer), → Order[] (buyer), → PrivateLabelRequest[], → Document[] (uploader) |
| `Session` | one per device login; `expiresAt`, `revokedAt`, `revokedReason`, `ipAddress`, `userAgent`; cascade on user delete | → User, → RefreshToken[] |
| `RefreshToken` | `familyId` (rotation chain), `tokenHash` unique (sha256), `issuedAt`, `expiresAt`, `rotatedAt`, `revokedAt`, `reusedAt`; cascade on session/user delete | → Session, → User |
| `VerificationToken` | `userId`, `purpose` (email_verification / password_reset), `tokenHash` unique, `expiresAt`, `usedAt` | (userId is a plain string, no FK) |

### 2.8 Documents

| Model | Key fields | Relations |
|---|---|---|
| `Document` | `kind` (rfq_attachment / quote_attachment / order_document / shipment_document / compliance / other), `originalName`, `storedFilename` unique (**random UUID + ext, server-side**), `mimeType`, `sizeBytes`, `checksumSha256?`, `ownerType` ("rfq" | "order" | "shipment" | "support_ticket") + `ownerId` (polymorphic — string pair, used for authorization), soft-delete | → User (uploader), → RfqDocument[] |

Files themselves are **not in the DB** — they live in `DOCUMENT_STORAGE_DIR`
(outside the web root); only metadata + signed-URL tokens touch the API.
Upload limit 10 MB; MIME allowlist: pdf, jpg/jpeg, png, webp, doc/docx,
xls/xlsx, csv, txt.

### 2.11 Audit log

| Model | Key fields | Relations |
|---|---|---|
| `AuditLog` | `action` (`AuditAction` enum, 21 actions: user_registered/login_failed/logout(_all), password_reset_*, email_verified, role_changed, rfq_created/status_changed, quote_created/accepted/rejected, order_created, shipment_created/status_changed, document_uploaded/downloaded, supplier_product_reviewed, admin_action), `actorId?` (nullable — system actions), `entityType?`, `entityId?`, `metadata` Json?, `ipAddress?`, `userAgent?`, `createdAt` | → User? **Append-only by convention** — no update/delete paths exist in the API.
Audit writes never break the request path: `AuditService.log()` catches and
logs failures loudly instead of throwing.

## 3. Index notes

Indexes are declared in the schema (see the `@@index` lines). Hot-path coverage:

- `User(email)`, `User(roleId)`, `User(deletedAt)` — login + role resolution.
- `Session(userId, expiresAt)`, `RefreshToken(familyId, sessionId, expiresAt)`,
  `RefreshToken(tokenHash)` unique — rotation + reuse detection.
- `Rfq(buyerId, status, rfqNumber, deletedAt)` — buyer listing + transitions.
- `Quote(rfqId, status)`, `Order(buyerId, status, deletedAt)`,
  `Shipment(orderId, status)`, `ShipmentEvent(shipmentId, occurredAt)`.
- `Document(ownerType, ownerId)`, `Document(uploadedById)` — per-document auth checks.
- `Notification(userId, createdAt)`, `Notification(userId, readAt)` — inbox + badge.
- `AuditLog(actorId, createdAt)`, `AuditLog(action, createdAt)`,
  `AuditLog(entityType, entityId)` — investigations.
- `Product(categoryId, slug, deletedAt)`, `Supplier(ownerId, status)`,
  `SupportTicket(requesterId, status, assigneeId)`.

Missing indexes are a tuning task once real query patterns emerge on staging —
do not add speculative indexes before then.

## 4. Migration workflow

| Command | When |
|---|---|
| `npx prisma migrate dev` | Local development — creates the DB, applies pending migrations, regenerates the client. |
| `npx prisma migrate deploy` | CI / staging / production — applies already-generated migrations, never creates new ones. Also runs automatically at container start (see `Dockerfile` CMD). |
| `npx prisma migrate diff` | Sanity check wired into the Docker build (`/tmp/schema-check.sql`) to fail the build if the schema and migrations disagree. |

Rules:

- Migrations are **forward-only** and reviewed. No destructive migration
  (drop column/table) ships without a backup and a tested restore (see
  `docs/deployment.md`).
- `DATABASE_URL` comes from the environment; the Docker build embeds none.

## 5. Seed policy

- `npm run prisma:seed` (`apps/backend/prisma/seed.ts`) inserts: 4 roles +
  permission grants, product categories, the **16 audit-verified products**
  (verbatim names/specs/order volumes), and 5 dev users
  (`buyer@example.com`, `buyer2@example.com`, `supplier@example.com`,
  `staff@example.com`, `admin@example.com` with the documented dev passwords).
- The seed **refuses to run when `NODE_ENV=production`** (hard guard).
- The Docker `CMD` runs `prisma migrate deploy` only — **the seed is not wired
  into any deploy path**. Dev-only seed data must never reach production.
- Production starts with an empty schema + a single admin user created through
  a documented bootstrap procedure (see `docs/runbooks.md` — still to be run;
  needs infra first).

## 6. Backup & retention (summary)

Full procedure in `docs/deployment.md`. In short: daily `pg_dump` snapshots of
the managed production database + point-in-time recovery, 30-day retention,
quarterly restore drill. Nothing is automated yet — provisioning is
needs-from-Sukh (TODO-needs-infra).

## 7. What the DB does NOT hold

- No prices on products (quotation-only model, matching the live site).
- No card/payment data — there is no checkout in v1.
- No file bytes (documents live on disk in `DOCUMENT_STORAGE_DIR`).
- No secrets in plaintext (hashes only).
- No analytics/tracking tables — analytics is provider-side (Crashlytics/GA4
  planned, not wired; see `docs/deployment.md`).
